Q23. Describe your application
================================================================================
The Process Intelligence Engine (PIE) is an enterprise AI application that transforms unstructured natural language descriptions of business and industrial processes into structured, evidence-backed transformation intelligence. PIE ingests raw process narratives, extracts bounded 1–5 ordinal ratings across 8 operational dimensions, verifies extracted claims against a 25-document industrial engineering corpus via lexical and dense vector retrieval with exact substring quote matching, computes deterministic scores and factor contributions using a configurable YAML rubric, and dynamically updates portfolio rankings and percentiles across 100 processes.


================================================================================
Q24. How does your application solve the business problem?
================================================================================
Enterprise operational transformations suffer from subjective consulting evaluations, misallocated automation budgets, and hallucinated AI advice. PIE solves this by implementing an objective, deterministic decision pipeline. Instead of relying on an LLM to guess scores or rankings, PIE bounds the LLM strictly to feature extraction and query routing. Pure deterministic Python software computes mathematical scores, applies compliance override rules, and validates verbatim quotes against ground-truth technical standards, delivering 100% auditability and mathematical explainability.


================================================================================
Q25. Why did you choose this architecture?
================================================================================
We adopted the core design principle: "AI interprets. Deterministic software decides." This decoupled architecture separates non-deterministic language understanding (Groq-hosted Llama 3) from deterministic business logic (Python scoring engine, YAML rubric, and PostgreSQL persistence). This guarantees mathematical consistency (the sum of factor contributions always equals the total score), eliminates prompt injection in database queries via typed QueryPlans, and provides full provenance for executive decision-making.


================================================================================
Q26. What makes your solution different?
================================================================================
1. Strict Separation of Concerns: The LLM never computes final scores, rankings, or arbitrary SQL queries.
2. Exact Substring Quote Verification: Claims are verified against reference texts using strict normalized substring matching—never probabilistic semantic similarity.
3. Linear Additive Explainability: Every score is decomposed into a visual waterfall of signed positive drivers and negative constraints.
4. Hard Safety Override Rules: Heavily regulated processes with high human judgment are automatically capped at 'Augment', preventing dangerous over-automation.
5. Zero Text-to-SQL Risks: Natural language queries map to closed intent schemas and whitelisted, parameterized SQLAlchemy executors.

Q37. Why you selected this AI approach and challenges
================================================================================
We chose a bounded, hybrid AI approach because enterprise operations demand precision and traceability. Pure LLM reasoning fails at arithmetic and compliance rules, while pure rules-based systems cannot parse unstructured natural language narratives. By combining LLM extraction with deterministic rubric scoring and exact quote verification, we get the best of both worlds. The primary challenge was designing resilient self-repair prompts and on-disk caching to handle API rate limits and strict schema validation.


================================================================================
Q38. AI Design Approach
================================================================================
Our AI design follows the "Bounded Extraction & Controlled Execution" pattern:
1. Narrow Cognitive Scope: The LLM is restricted to reading text and emitting structured JSON ratings and claims.
2. Immutable Rubric Decoupling: Scoring weights are stored in an external, human-readable YAML rubric, allowing business analysts to tune weights without touching LLM prompts or code.
3. Verifiable Provenance: Claims are anchored to physical documents with verbatim quotes.
4. Whitelisted Query Routing: Natural language Q&A is routed through strict Pydantic QueryPlans to pre-compiled SQL queries.


================================================================================
Q39. AI Layers
================================================================================
1. Cognitive Extraction Layer: Groq Llama-3.1-8B parses raw process narratives into 8 standardized ordinal attributes (1–5).
2. Semantic Retrieval Layer: sentence-transformers (all-mpnet-base-v2) generates 768-dim embeddings stored in pgvector.
3. Deterministic Decision Layer: Pure Python scoring engine computes signed contributions and applies safety overrides.
4. Ground-Truth Verification Layer: Substring matcher confirms quote authenticity in source texts.
5. Conversational Query Routing Layer: Intent classifier translates user questions into typed QueryPlans.


================================================================================
Q40. AI Processing Workflow
================================================================================
1. Raw Text Submission -> Regex Normalization & SHA-256 Deduplication.
2. Groq JSON Extraction -> Ordinal ratings (1-5), confidence scores, rationales, and 3-5 factual claims.
3. Feature Normalization -> Ordinals mapped to [0.0, 1.0].
4. Dual-Engine RAG -> Lexical + pgvector retrieval against 25 corpus docs.
5. Verbatim Quote Selection -> LLM identifies candidate quotes; Python validates exact substring existence.
6. Mathematical Scoring -> Rubric weights × signed values × 100 + Safety override evaluation.
7. Portfolio Ranking -> Instant recomputation of ranks and percentiles across all scored items.


================================================================================
Q41. Knowledge & Context
================================================================================
PIE embeds a curated knowledge base of 25 industrial engineering reference standards (ISO 13373 for vibration diagnostics, IEC 62443 for industrial cybersecurity, IPC-A-610 for electronic assembly, FDA 21 CFR Part 11 for pharma compliance, Six Sigma SPC, Lean 5S, and MES architectures). Documents are chunked into ~500-token segments with 80-token overlaps, embedded via all-mpnet-base-v2, and indexed in pgvector.


================================================================================
Q42. AI Reasoning
================================================================================
To guarantee reliability, complex multi-step reasoning is split between cognitive and deterministic modules: the LLM performs qualitative semantic reasoning (evaluating whether a process description indicates high or low rule clarity), while the Python engine performs quantitative and logical reasoning (evaluating weighted sums, applying threshold band cutoffs, and checking regulatory safety override predicates).


================================================================================
Q43. Reusability
================================================================================
The architecture is completely domain-agnostic and reusable:
- Interchangeable Rubrics: The rubric YAML can be swapped (e.g., from Manufacturing to Financial Services or Healthcare) without altering backend code.
- Pluggable Corpus: Adding new Markdown documents to app/corpus/ automatically chunks, embeds, and indexes them upon server restart.
- Extensible Intents: New QueryPlan intents can be registered in plan.py and executors.py in under 20 lines of code.

Q52. Most difficult part
================================================================================
The most challenging aspect was establishing the exact boundary between probabilistic LLM extraction and deterministic software execution. Specifically, ensuring that open-weights LLMs reliably adhere to bounded JSON schemas (ratings 1–5), developing a robust self-repair prompt loop for malformed responses, and designing the deterministic quote verification algorithm so that evidence claims are strictly grounded in source texts without false-positive matches.

Q54. What did you learn?
================================================================================
We reinforced the vital lesson that enterprise AI success is 90% software engineering and 10% model prompting. LLMs excel at semantic interpretation, but business stakeholders require deterministic predictability, mathematical accuracy, and auditability. By restricting the LLM to structured feature extraction and routing while letting deterministic Python code execute scoring and SQL queries, you eliminate hallucinations and build genuine enterprise trust.
